# Project instructions

## Required work log

The user requires an English work log and wants every subsequent project operation recorded.

- Read `WORK_LOG.md` before starting work in this project.
- Append a timestamped English entry for each operation: investigation, file/code/documentation/configuration change, test, build, real API check, deployment, or rollback. Record failed attempts and their resolution as well as successful operations.
- Use Asia/Shanghai time (UTC+08:00). Include the action, result, verification evidence, and any remaining limitation. Do not invent timestamps or claim unperformed checks.
- Consecutive low-level reads or browser interactions for one investigation may share an entry, provided the entry describes the actions and outcome. Preserve a separate record for each meaningful change or check.
- Keep historical entries. Correct errors with a dated correction rather than silently rewriting the history.
- Never include API keys, tokens, passwords, authentication headers, secret values, or real customer personal information. Describe secret configuration by variable name and status only. Use fictional data for recorded examples.
- Before the final response, record all operations performed during the turn, including verification and deployment outcomes, or explicitly state what could not be completed and why.
- Updating the work log does not itself require another recursive log entry. Do not run tests or deploy the website solely because its documentation or work log changed.

This instruction applies to future work in this project. It does not create a scheduled or background task.
